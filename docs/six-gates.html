六道关卡

把一批试验数据做成一份经得起追问的交付物，中间要过六道关——编号与 /analysis-sprint 一一对应。这张图讲它们各自守什么、以及为什么必须是六个而不是一张大清单。

数据分析出错的地方不是均匀分布的，它们集中在交接口——数据换手、表变成数、数变成话、话变成产物。而每个交接口有一个共同性质：下游的检查，发现不了上游的错误。

主线关卡按材料流动排序，编号跟 /analysis-sprint 走（条件关：外部数据才走）；上下两条横切带不在流水线上，任何时刻都可能需要
横切 long-task-collaboration — 任何正要开口问人、正要汇报的时刻

交接契约

看最后一列——那就是上面那条论点的具体形式
关卡交出去的东西它假定上游已经做完了
data-source-skepticism一批身份已确认、适配性已验的数据——
analysis-groundwork一张口径已固化的分析表 ＋ prep 脚本 ＋ sanity print数据是真的
statistical-caliber一组带口径、经得起追问、非统计读者能懂的数字与措辞每一档本身算对了
generated-deliverable-discipline一份可复现、数字绑定、验证过的产物数字和措辞已定稿
口径错了（谁和谁可比），statistical-caliber 的每一条检查都会通过——因为它假定每一档本身算对了。数据源错了，地基上所有判断白做。
这就是为什么是六个而不是一张大清单：大清单会让你以为"我全过了一遍"，而真正决定成败的是顺序和前置假设。

主线关卡（一～五）

醒来时刻 / 守什么 / 标志性判据 / 真实翻车现场

data-source-skepticism

关卡二 · 条件

醒来：别人给了你一批数据，或者你从 API 抓了一批。

先搜自己地盘有没有同源旧数据（判定力高于统计指纹）→ 查取数代码的实际参数（最危险的是没写的参数）→ 适配性四项 → 需要时做指纹判定。另有独立一节：量化天花板——别人问"能不能更准"时，先算"就算全做对天花板在哪"。

标志性判据「太干净」是嫌疑，不是优点。
翻车现场一个漏掉的 API 参数，让接口回退到"自动挑最好的模型"默认档。此后连续几轮汇报都把数据称作原以为的那个源——而数据看起来完全正常。

analysis-groundwork

关卡一

醒来：一张 Excel/CSV 摆在面前，你正要写第一行 groupby。

逐列点名（把"我从没打开看过"的列当一级风险）→ 口径盘点按爆炸半径分承重／可延后 → 承重的停下来等人答。

◆ 停止点 — 承重口径必须等人拍板

标志性判据同一份文档里两处计数对不上 ＝ 报警器。不许当四舍五入糊过去。
翻车现场缺失值在拼分组键时彼此相同，静默并出一个不存在的组，独立单元 35 → 36，一整组统计作废。另一次：编码语义读错，"干净对比" 55 → 96 条，头条在 p=0.055 不成立 ↔ p=0.0019 成立 之间翻了个面。

statistical-caliber

关卡三 · 四

醒来：你正要写"提升 X%"、"显著"、"相关"。

口径阶梯并排列出（同一个量在多个口径下都是真的）＋ 十条清单逐条过 ＋ 分层可下钻表达（外层通俗、下钻第一句永远先答"为什么需要这一步"）。

◆ 停止点 — 主口径只定一个

标志性判据换一个同样合理的口径，这条结论会不会垮？会，就必须说出来。
翻车现场把趋势检验的 p 值配给了分档提升的量级——数字都是真的，配对是错的。另一处：稳健性对照用了不同量纲的估计量，而且偏差方向恰好对结论有利。

generated-deliverable-discipline

关卡五

醒来：改报告、改 deck、更新数字、验收图表。

锁边界（工作区干净）→ 验真源（产物与脚本重生成逐字节一致）→ 改脚本不改产物 → 固定顺序验证，便宜的先跑（重跑 → 语法 → 秒级数值断言 → 浏览器体检 → 逐页看图 → 交互实测 → diff）。

标志性判据「体检报 0 问题」≠「可以交」。机器查几何，人眼查审美，实测查交互。
翻车现场一页排版塌了，自动体检报 0 问题、一整套多 agent 验证流程全绿；最后是收件人自己贴了张截图才发现——流程里根本没有人真的看过图。

两条横切

不在流水线上，任何时刻都可能需要；其中 verified-survey 同时押尾为关卡六

long-task-collaboration

横切 · 人

醒来：要提问、要汇报、子 agent 回来了、被说"你怎么没做"。

它插在每个关卡的停止点上：地基的承重项、主口径选哪一档、编码字段什么意思、产物验收。

标志性判据我问的这个问题，他有 context 回答吗？选项里引用了他还没被你带着过一遍的东西，就不能问——先讲清，下一轮再问。
翻车现场一次问了三个问题：第一个凭身份就能答，当场被回答；后两个引用了 agent 自己刚读出来的产物和数字，两问全部空白并被驳回。

verified-survey

关卡六 · 横切 · 确信

醒来：对象大到一个 context 装不下，或者结论要拿去做决定。

并行调研 → 对抗核验（默认立场"这是误报"）→ 综合 → 完整性批评者。它和其余五个是元关系：核验的是它们的产出。

标志性判据有没有人试图推翻过这些发现？没有的话，规模只是在批量生产待核实的猜测。
翻车现场脚本里写着"先去重再核验"，紧跟的代码只有一个按严重度过滤——去重从来没实现。同一件事被两个方向各报一次，一条判成立、一条判推翻。
起编排时有一条容易漏：把纳入规则和分组键也显式塞进核验队列。它们不在任何 findings 数组里，所以结构上没人会去证伪它们——而那正是最贵的两次错误所在。

顺序不是死的

取决于数据从哪来
数据来源先走哪个为什么
别人给的 / API 抓的data-source-skepticism → analysis-groundwork在假数据上设计可比性是白做
你自己的试验记录analysis-groundwork 先行源头没疑问，问题在可比性
上一个项目两种都有：试验表是自己的（地基先行），天气数据是外部抓的（源头怀疑主义，后来真的翻车了）。所以 /analysis-sprint 里数据源那一关标成了条件关卡——数据不是自己生成的才走。

下次 sprint 实际怎么走

/analysis-sprint
00
开场四问数据形态 · 要回答什么 · 交付物给谁 · 有没有上一版。第四问是特意加的，它决定后面所有"两版数字对不上"的争论。
01
地基 — 逐列点名，产出承重／可延后两档清单，然后停◆ 整条链上最省钱的一次等待。上个项目里编码语义读错让头条翻面，就是因为这一停发生得太晚。
02
外部数据（如果这季又要拉天气／土壤）先适配性（便宜、常常直接否掉），再真伪（贵）。
03
算 ＋ 判断每个数能不能这么说主口径只定一个，全文头条统一用它；其余档进阶梯表和附录。
04
讲给谁听方法卡、四层下钻、外层不出现裸的 p 值／相关系数／区间端点。
05
做产物数字从数据文件渲染、加构建后断言；图表先过"有没有替读者下结论"那一档，再过逐项清单。
06
交付前核验装得下就自己读，别起编排；起编排就带上完整性批评者。
全程：每次汇报挂一段「还欠着的」，下一轮从它开始；子 agent 的结果不许原样转发，要重新综合成分层 ＋ 编号 ＋ 带位置和改法的清单，末尾把调度权交还。
