# 生成型交付物的改动纪律

## 适用场景

项目形如 `数据 → prep 脚本 → 中间产物 → build 脚本 → 交付物`。交付物（HTML 报告、幻灯片、静态站点、生成的文档/图表）**不是手写的**，是渲染出来的。

这类项目的失效方式几乎全是**静默的**：改动跑通了、文件生成了、看起来正常，但内容错了。所以纪律的重点不是"小心点"，而是**把静默失败变成显式失败**。

---

## 第一步：锁边界（动手之前）

### 确认工作区干净，记下起点

改之前确认版本控制里没有未提交的改动，并记下起点 commit。

**为什么**：这样事后一条 `git diff` 就**精确等于本轮全部改动**，不多不少。有了这个，才可能做最后那一步 —— 审查 diff 找**越改**（改了没被要求改的东西）。工作区本来就脏的话，diff 里混着别的东西，越改就查不出来了。

如果工作区不干净：先弄清那些改动是什么、是否要保留，别直接盖过去。

### 验真源：产物真的是脚本生成的吗？

**改脚本之前，先证明现有产物 = 脚本重新生成的结果，逐字节一致。**

做法：把脚本输出到临时目录，与已交付的文件 `diff` 或比对哈希。

**为什么这一步不能省**：如果不一致，说明产物**被手改过**。这时你一改脚本重新生成，那些手改的内容会**静默消失** —— 没有报错，没有冲突提示，只是某段文字悄悄回到了旧版本。而且往往几周后才被发现。

不一致时不要直接继续。先查清差在哪、是谁改的、要不要保留 —— 手改的内容要么合并进脚本，要么明确放弃。

---

## 第二步：改脚本，不改产物

所有改动落在生成脚本上，产物由脚本重新生成。

**会诱惑你破例的时刻**：只改一个错别字、只改一个数字、赶时间、"这处脚本里太难找了"。破例一次，真源就断了 —— 下一次任何人重新生成，你的改动就没了，而且没人会知道。

真要临时手改，就当场记下来并在同一轮补回脚本里。

---

## 改一个数之前：先列出它的派生字段

**改真源里任何一个数值之前，先把数据文件里所有可能由它推导的字段列出来**（提升幅度、占比、差值、排名、显著性、以及任何"相对于对照"的量），逐个判断要不要同步改。

**为什么这条容易漏**：改一个数感觉像单点修改，而派生量往往和它并排躺在同一个 JSON 里、看起来同样是"原始输入"。结果是产出一份**内部自相矛盾**的产物 —— 正文用了新值，括号里还挂着基于旧值算出来的提升幅度和 p 值。它不会报错，构建照样成功。

> 真实案例（本 skill 的评测里抓到的）：数据文件里同时存着 `conversion_rate`、`uplift_pct`、`p_value`。只把转化率从 4.31 改成 4.58，就会生成一份"转化率 4.58%、较对照提升 12.4%、p=0.031"的报告 —— 后两个数是基于 4.31 算的，已经对不上了。

规则：推导得出来的就一起改；**推导不出来的（比如 p 值需要原始数据重算），把追问一次性提给人**，不要默默留着旧值。

## 停手的门槛：分清"保全"和"决定"

发现问题要停下来问人时，**不要连零成本、可逆、不改变产物的保全动作也一起停掉**。

- **该做了再报告**：把手改内容回填进模板并验证"模板 + 当前数据能逐字节复现现有产物"、把现状比对结果落到临时目录、列出受影响的派生字段。这些纯增量、随时可回滚、不动交付物。
- **该停下来问**：会覆盖交付物、会丢失内容、会推翻一个已经对外说过的口径、或者需要领域判断（这段临时说明还要不要）。

把两者混为一谈，会让人收到一份"我什么都没做，请指示"的答复 —— 而其中一半的活你本可以安全地做完并顺手验证。

---

## 第三步：定位改动点用锚文本，不用行号

多 agent 协作或分两步做（先取证定位、再实施修改）时，**位置要用能唯一定位的上下文描述**（函数名、元素 id、附近的独特字符串），**不要只给行号** —— 文件在这轮里会被改多次，行号会漂。

同样地，要替换的原文片段必须**逐字准确**摘录，否则精确替换会失败或误伤。

**并行的边界是文件**：改同一个文件的任务必须串行；不同文件之间才能并行。同一文件并行改会互相覆盖。

---

## 第四步：改完的固定验证顺序

顺序是固定的，理由有两条：**前一层不过，后面几层的结果没有意义**；以及**便宜的先跑** —— 一秒能否掉的事，不要拖到开浏览器才发现。

### 1. 重跑生成脚本 —— 能不能生成

最基本的一层。顺带看脚本自己打印的 sanity check（输出字符数、行数、记录条数）。**廉价的自检打印值得加**：数量级不对一眼就能看出来，成本几乎为零。

### 2. 语法检查生成出来的代码

如果产物里含有内联脚本/样式，**把它抽出来跑语法检查**。

**为什么必须单独查**：生成出来的代码的失败模式是**静默的**。

> 真实的坑，踩过多次：模板字符串用反引号开头、却用单引号收尾，会**静默吞掉后面所有代码** —— 文件照样生成、页面照样打开、只是后半段功能全没了，浏览器控制台可能什么都不报。

推广：**任何"字符串拼出来的代码"都会有这类静默失效**（引号配对、转义、注入的 JSON 里含有结束定界符）。一次语法检查是最便宜的保险。

### 3. 数值断言（秒级、只读、不开浏览器）

见下面「数值与文案的绑定」一节。

**它必须排在版面体检之前，并且做成一个独立的秒级子命令。** 数值断言是纯文本比对，零点几秒返回；版面体检要启动无头浏览器逐页扫，几十秒起。**跟慢检查捆在一起的断言，实际上没人会在每次改完之后跑** —— 而它恰恰是最该每次都跑的那个。

### 4. 结构体检（机器查，要开浏览器）

跑自动化的版面/结构检查。机器擅长的是**有明确判定标准**的缺陷：

- 元素两两重叠
- 容器滚动溢出（内容比容器高）
- 文字越出图形边界
- 元素越出栏位边界

**要在多档视口都跑** —— 固定舞台的产物在不同视口下缩放不同，只在一档下没问题不代表另一档没问题。

### 5. 逐页截图，**真的把图读出来看**

**机器查不出"丑"。** 「0 重叠、0 溢出」和「好看」是两回事。

> 真实案例：某页因为网格行高与对齐方式的组合，出现一大片死白。自动体检报 0 问题，**一整套多 agent 的修复 + 验证流程全绿**；最后是**收件人自己贴了一张截图、一句「这个块排版有点问题」**才发现。
>
> 教训不是"截图能发现问题"，是**流程里根本没有人真的看过图** —— 每一层都在查自己那类缺陷，而"好不好看"不属于任何一层。

规则：**逐页截图并实际查看图像内容**，不是确认截图文件存在。机器看不见的那类问题是：留白失衡、视觉层级错乱、对齐看着别扭、颜色语义用错、信息密度忽高忽低。

图表另有一套专门的验收项，见下面「图表可读性验收」一节。

### 6. 交互实测

跳转、弹窗、切片器、筛选这类，**真的点一遍，核对落点**。

> 真实案例：页内跳转有 8/10 指向错误的页 —— 页码索引是旧版式遗留的，改版后没跟着更新（这一条是**把导航定义和实际索引逐个对照读源码**查出来的）。
>
> **实测买到的是另一个教训**：索引改对之后再实测，才发现其中一处修复落在了一段 `display:none` 的死代码上 —— 元素实测宽高为 0，用户永远点不到。**改对了 ≠ 生效了。**

顺带一条：**跳转的落点改了，卡面上写的"详见第 X 页"也要跟着改。** 只改索引不改文字，仍然是错的。

### 7. 审查 diff，找越改

对着第一步锁定的起点看完整 diff。逐处问：**这一行能不能追溯到本轮的某条需求？** 追溯不到的就是越改 —— 要么撤销，要么明确说明为什么留。

## 图表可读性验收

**图表很少一次做对。** 预算里要留出迭代轮次，并且**让没画这张图的人（或另一个 agent）来看** —— 画的人知道每个元素是什么意思，看不出别人看不懂。

### 先问：这张图要说的那一个点是什么？

一张图说一件事。**说不清就拆成两张**，不要靠读者自己从一堆线里找出你想让他看的那条。

### 最高优先级：这张图有没有替读者下结论？

下面那些逐项检查抓的是"**读不清**"；这一档抓的是"**读错**"。机器体检一条都报不出来，而它造成的损害最大。

- **最强的视觉信号，是不是对应结论里最弱的那条？** 一根特别高的柱子、一条特别陡的线，读者会自动认为那是主结论 —— 如果它恰好是那个样本量最小、或没过校正的发现，图就在替你说一句你不敢写的话。
- **图上画的方法，和正文引用的统计量是同一个吗？** 正文说的是偏相关，图上画的是原始散点加拟合线，读者会把两者当成一回事。
- **轴的量程是不是被离群值或已作废的旧值撑开了？** 量程一变，同样的差异可以看起来很大或几乎没有。
- **有没有把"没有差异"画成了"有差异"？** 截断轴、非零起点、放大的纵轴，都会让噪声看起来像信号。

判断方法：**只看图、不看文字**，把它讲一遍。讲出来的和正文结论不一致，改图。

### 逐项检查（按学术图表的标准）

**坐标轴**
- 每根轴有标题吗？**带单位吗**？
- 刻度可读吗（不要科学计数法、不要挤成一团、不要旋转 90° 才放得下）
- 柱状图的数值轴**必须含零**；不含零的截断轴必须显式标出断口
- 同一份产物里同类图的轴范围一致吗？不一致会被读成差异

**图例**
- 存在吗？和数据的对应关系明确吗（颜色/线型能对上）？
- 会不会压住数据点或标注？
- 位置在同类图之间一致吗？
- 只有一个系列时，图例其实可以删掉，改成直接标在线上

**标注与文字**
- 小标、注释、数据标签有没有被裁掉、互相重叠、越出画布？
- **最小字号覆盖检查**：语义必需的文字有没有低于阈值？在**实际展示尺寸**下还读得清吗？
- 数字的有效位数一致吗？（一处写 2.6%、另一处写 2.57% 会让人以为是两个数）

**边缘与留白**
- 有没有元素贴边、被裁、或压住边框？
- 数据区四周留白够不够？密集处有没有挤在一起？

**颜色**
- 颜色语义在整份产物里一致吗（同一个含义永远同一个颜色）？
- 灰度打印和色觉障碍下还分得开吗？不要只靠颜色区分关键类别，加形状或直接标注

### 交互图额外

- **默认状态是有意义的吗**？默认空白/全选/无数据，读者第一眼就迷路
- hover / 点击 / 切片器的落点对不对？切完之后**图和旁边的文字还一致吗**（最常见的不一致来源）
- 交互失效时是否还能读懂（截图进 PPT、打印、导出 PDF 的场景）

### 最后一步

**把图放到实际展示尺寸下看一眼。** 设计时在大屏上缩放着看，和会议室投影、手机上看，是三件不同的事。

> 图表的配色体系、图形选型、色板可访问性这些**设计层面**的问题，用 `dataviz` skill；这一节管的是**验收**——已经画出来的图有没有硬伤。

## 数值与文案的绑定：让旧数字不可能残留

报告里的统计数字最隐蔽的失效方式：**数字是手打进模板的**。数据更新了、口径改了，文案静默过期，谁也不知道。

解法两层。

**第一层：从数据渲染，不要手打。** 数字从数据文件（JSON）读出来注入模板，而不是写死在字符串里。

**第二层：加构建后断言**，检查产物里的数字与数据文件一致，并且作废的旧值没有残留。

### 断言的设计难点：为什么裸黑名单会失败

直觉做法是"禁止出现旧数字"。**这行不通**，因为作废的旧值经常会以**完全合法的形式**重新出现 —— 方法论章节要讲"同一个量在不同口径下分别是多少"，就必须原样引用那个旧数字；历史对比、版本说明同理。裸黑名单会把这些合法引用一起打掉，于是很快就被加一堆例外，最后没人再信它。

**可行的解法是上下文判定**：不禁止这个串出现，而是要求**它每一次出现的前后 N 个字符内，必须有口径限定词**（说明这是哪一档的那个词）。合法引用天然满足 —— 引用它就必须说明它是哪个口径的；从旧版复制过来的裸句子天然不满足 —— 旧版那会儿根本没区分口径。

实现上的两个要点（都是踩出来的）：

- **把产物压成纯文本再判定**，因为数字常被行内标签包着（`p=<b>0.03</b>`），不去标签就匹配不上。
- **但要在段落/块级边界处截断窗口**，否则"上一段结尾恰好有个限定词"会把下一段的裸残留洗白 → 漏报。行内标签整个删掉不留边界，块级标签换成边界哨兵。

### 断言要分档

- **硬问题**（必须修）：作废口径裸残留、明令禁用的措辞、权威值在产物里一次都没出现（说明绑定断了）。
- **提示**（不计入失败）：出现次数低于历史基线（可能"只绑了一半"）、源码里检测到手打字面量。

分档的理由：正常增删文案也会让计数变化，把这类做成硬失败会让人开始忽略断言。**一个经常误报的断言，等于没有断言。**

### 断言必须自测

**造几个假的残留塞进产物副本，验证断言确实会报错；再拿合法引用验证它不误报。**

不自测的断言极容易写成"永远通过的空壳"（正则写错、路径不对、大小写不匹配），而它每次都绿，你会越来越信它。

### 留逃生舱

给断言一个明确的豁免机制（行尾注释标记、定义块自动豁免），并要求写明豁免理由。没有逃生舱的检查，遇到第一个合理例外就会被整个关掉。

### 扫描范围要划清

只扫**当前主交付物**。历史版本、归档报告、以及讨论"旧说法应该改成什么"的元文档里，旧数字本来就该在 —— 全目录扫必然误报。

## 三种验证的分工

| 交给谁 | 查什么 | 查不出什么 |
|---|---|---|
| **机器（结构检查）** | 重叠、溢出、越界、数值绑定 | 丑、失衡、语义用错 |
| **人眼（逐页看图）** | 排版观感、视觉层级、留白、颜色语义 | 大规模一致性、精确数值 |
| **实测（真的点一遍）** | 跳转落点、弹窗、筛选、状态切换 | 静态外观 |

三者不能互相替代。**「体检 0 问题」不等于「可以交付」。**

## 红旗表

| 想法 | 现实 |
|---|---|
| 「体检报 0 问题，好了」 | 0 重叠 ≠ 好看。逐页截图自己看。 |
| 「就改一个字，直接改产物快些」 | 真源断了，下次重新生成你的改动就没了。 |
| 「脚本能跑通、文件生成了，应该没问题」 | 生成型失败是静默的。查语法、查数值、看图。 |
| 「截图了」 | 截图 ≠ 看了图。真的把图读出来。 |
| 「跳转索引改对了」 | 卡面文字里写的"第 X 页"也改了吗？ |
| 「断言跑绿了」 | 断言自测过吗？空壳断言永远绿。 |
| 「加个黑名单禁掉旧数字就行」 | 旧数字有合法出现的场合。用上下文窗口判定。 |
| 「顺手把这段也整理了」 | 越改。diff 里每一行都要能追溯到需求。 |
| 「上一轮已经验证过了」 | 自己再跑一遍。别人的"验证过"不算数。 |
| 「图我画出来了，数据是对的」 | 数据对 ≠ 读得懂。轴/图例/字号/边距逐项过一遍。 |
| 「这张图信息很全」 | 一张图说一件事。说不清就拆两张。 |
| 「我看着挺清楚的」 | 你知道每个元素是什么意思。找没画这张图的人看。 |
| 「设计稿上看着没问题」 | 到实际展示尺寸下再看一次（投影、手机、打印）。 |
| 「就改这一个数，很简单」 | 数据文件里哪些字段是它的函数？提升幅度、p 值、排名会一起过期。 |
| 「有疑问，先停下来问，最安全」 | 零成本、可逆、不动产物的保全动作先做完再问。别交一份"我什么都没做"。 |

## 与其他 skill 的关系

- 交付物里的**统计数字能不能这么说** —— 见 `statistical-caliber`。
- 数字背后的**数据本身可不可信** —— 见 `data-source-skepticism`。
- 用多 agent **系统性审查并批量修改**一份交付物 —— 见 `verified-survey`。
- **改之前先请人点单、改完怎么汇报**（评审只读、分层清单、"还欠着的"）—— 见 `long-task-collaboration`。
- 产物上游那层 **prep 脚本怎么把口径固化成唯一真源** —— 见 `analysis-groundwork`。
