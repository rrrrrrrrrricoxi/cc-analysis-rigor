# 四段式：调研 → 对抗核验 → 综合 → 完整性批评

## 为什么是四段

派一批 agent 并行调研，回来的是一堆**看起来都很有道理**的发现。问题在于：没有人试图推翻过它们。经验上，一次调研报上来的"风险"里有相当比例是误报 —— 看错了文件、把归档的旧版本当成当前产物、把不同口径的数字当成矛盾。**把这些直接写进结论，等于用规模换来了更多的错。**

所以中间必须有一段专门用来杀掉误报，末尾必须有一段专门用来找"没被问到的问题"。这两段最容易被省略，也是这套方法真正的价值所在。

**先说成本**：这套编排很贵（几十个 agent、上百万 token、按小时计）。**不要对以下任务用它**：
- 一个 context 装得下的对象（几个文件、一份短文档）—— 自己读更快更准
- 答案唯一且可直接验证的问题（这个函数在哪、这个值是多少）
- 探索性的、还不知道要找什么的阶段 —— 先自己摸清楚，再决定往哪派人

**该用它的信号**：对象大到装不下、需要独立视角互相制衡、结论会被用来做决定、或者漏掉一个问题的代价很高。

## 第一段：并行调研

### 按"证据在哪"拆方向，不是按"话题"拆

每个 agent 分到一个**能独立取证的地盘**，彼此重叠越少越好。

**先确定这个任务的工作单元是什么，再按那个轴切。** 工作单元可能是产物层、数据对象、一条待决定的问题、一个生产要素 —— 切法是从任务性质推出来的。

> 某次摸项目现状用的是：生成流水线 / 交付产物 / 遗留代码 / 数据层 / 项目管理系统 / 版本历史。那是从「工作单元是产物层」推出来的，**不是模板**。照抄这张单子就废了 —— 换个任务，正确的切法可能是"一条 lane 对应一个待决定的问题"。

**至少留一路看向对象之外。** 这是最容易漏的一路，也常常是收获最大的：项目管理系统里的外部承诺、版本历史里的时间线、别的团队的文档。只盯着对象本身，你会得到一份"对象内部整改清单"，而不是"这件事现在什么状况"。

### 给所有 agent 同一份简报

写一段共享 context，每个 agent 的 prompt 都带上。里面放：

- **背景**：这是什么项目、当前处于什么阶段
- **已确认为真的事实**（尤其是关键数字/口径）—— 但**每条既有事实都要标出处 + 标要不要重算**，三档措辞不能混：
  - 「我亲自从中间产物复算，逐位吻合，**直接用，不要重算**」
  - 「前一个编排查出来的，**可作为线索，但报告里用到的数字请自己复算一遍**」
  - 「我已经实测出来的，**可直接用，但请自己复核**」
- **已被推翻的旧说法**，并注明不得出现在结论里
- **术语约定**
- **读者是谁、他的偏好是什么**
- **权限围栏**（见下）

**为什么要预先核实并共享事实**：不然 N 个 agent 会各自推导出略有出入的版本，综合时你要花更多时间去调和一堆本可以避免的分歧。核实一次，广播一次。

### 但要给这份简报单独派一个核验者

简报里标成"已确认"的前提会被每个 agent **无条件继承**，而所有针对**结论**的核验都测不到它 —— 它不在任何一条 findings 里。一条错前提会同时污染下游全部结论、图表和措辞，**而且在每份产物里都自洽，看不出破绽**。

核验前提的方式是**回到原始源重新生成一遍再比对**，不是读产物、不是读文档。

> 真实案例：一条「我们用的是某某数据源」的前提被写进三个编排的共享简报，其中一份还写着"已确认，视为已知，不要重新推翻"。真相是抓数脚本少了一个参数、接口默认回退到拼接模式，用的其实是另一个模型。发现它的 agent **并没有被派去查这件事** —— 它是因为被要求"复核我的探测结论，换几个点位、换几个日期再试，确认这是产品限制而不是偶发"，顺手把候选源重抓了一遍逐日比对才撞出来的。**这是运气，不能靠运气。**

### 明确写出权限围栏

每个 agent 都要知道它能做什么、不能做什么。最常用的是只读围栏：

> 【严格只读】不要修改、生成、删除任何文件。不要运行会覆盖产物的脚本。只读命令可以跑，但如果需要安装依赖就放弃并如实说明。

最后半句很重要：**预先告诉 agent 遇到障碍时该怎么办**（放弃并说明 / 换个方法 / 跳过），否则它会自作主张地装东西、改配置、或者编一个答案。

### 用 schema 强制拿出证据

这是让调研可信的主要机制。要求结构化输出，并且**每条断言都必须配一个证据字段**，在字段描述里**写死可接受的证据形式**：

```
facts:  [{ claim: '一句话事实陈述',
           evidence: '文件路径:行号 或 命令输出片段' }]
risks:  [{ title, detail, severity: high|medium|low,
           evidence: '同上' }]
openQuestions: [ ... ]
```

`evidence` 字段的描述里写清"文件路径:行号 或 命令输出片段"，比在正文里说"请给出证据"有效得多 —— 它把"发表意见"这条路堵死了。

同时要一个 `openQuestions` 之类的字段，**给 agent 一个诚实说"我没查出来"的出口**。没有这个出口，不确定的东西会被写成确定的。

### prompt 要具体到可执行

一份好的调研 prompt 长这样：编号的问题清单、点名要读哪些文件、给出要搜的关键词、说清什么算严重、并预先点破容易搞错的地方。

几条实测有效的措辞：

- **「读全文，不要只看开头」** —— 不写这句，长文件经常只被读了前几十行。
- **「不要相信任何外部给你的行号，文件已改过多次」** —— 让它自己定位。
- **「如果某个依赖不可用，如实说明并跳过」** —— 给出遇阻时的正确行为。
- **「这一轮是评估，不是改造」** —— 划清本轮的动作边界。

## 特例：派 N 个 agent 各查一部分同类数据

要把 N 个 agent 的结果拼成一张表时（各查一个地区/时段/产品线），**「把口径写进 prompt」不等于结果统一**。外部来源各有各的统计惯例；agent 找不到你要的口径时，默认行为是**交付它找到的那个，并且不主动声明差异** —— 因为没有任何地方要它声明。

> 真实的 A/B：同一个任务前后跑了两次，中间只改了 schema。
> **第一次** —— 时间窗写在 prompt 里，schema 里全是 `string`、没有口径字段。5 个 agent 交回来的实际是五种不同的时间窗（有的是另一个季度、有的只有一个城市、有的是不连续时段拼接的估算），而且**从结果里看不出来**，直到下游拼表时才暴露。
> **第二次** —— 加了必填的 `window` 字段和一句「如实记录，不要硬套成我给的窗口，也不要编造换算」，5 个里 3 个**当场如实报告口径对不上**。

五条做法：

1. **口径要有回传字段。** 规定是单向的，必须配一条反向通道才闭环：加一个必填的「你实际取到的口径」字段，并明确写「**不要硬套成我给的口径，也不要编造换算**」。

2. **要汇总的数值维度用 `number | null`，不要用自由文本。** agent 在自由文本里通常是诚实的（会写"估算""非官方"），但**这些标注和数字挤在同一个字符串里，下游抄进对比表时数字被抄走、caveat 被抄丢**。类型化把"我没有"逼进一个机器可查的槽位。

3. **不要用 agent 自评的 `confidence` 判断质量。** 它回答的是"我对我找到的数字有多确定"，不是"我有没有回答你的问题" —— 两个方向都会骗你。
   > 同一批结果里 5 个 agent 的 confidence **全是 medium**，包括 5 个字段全空的那个；而 null 计数（2/5 到 5/5）和 window 字符串一眼就把好坏分开了。
   **质量要从机械可校验的字段推导**：回传口径是否等于规定口径、必填数值里有几个 null、来源里有没有原文引语。

4. **结果回来的第一个动作是打一张定宽对齐表，口径列排在所有数值列之前。** 口径不一致**只有并排时才可见**；逐个打印摘要会让五种不同的窗口分散在五个段落里，还容易把末尾的 caveat 截断掉。

5. **允许 null，但 null 要附检索日志**（查了哪些具体来源、为什么没查到）。这让 null 从噪声变成一条有信息量的负面结论，也能区分"agent 偷懒"和"数据真的不存在"。

**口径要钉到公式、参数取值、单位、聚合方式，不能只写指标名。** 指标名是行业共识，公式不是 —— 同一个名字下两种都合法的教科书定义，在同一批数据同一个窗口上可以差 70%。

**最后：拼不齐时不要继续调 prompt。** 发布方的口径你改不了，N 个发布方就是 N 套口径，再多约束也只能让 agent 更诚实地报告不一致。正解是**降级到一个覆盖全部单位的原始逐单元数据源、自己算指标** —— 口径由构造保证一致，样本量往往还顺带变大。并且**把"拼不齐"本身当作结论写进产出**，那不是空手而归。

## 中间：barrier 去重（最容易只写成注释的一步）

调研全部回来后**先合并再进核验**，把重复的发现去掉。

这是少数**真正需要 barrier**（等齐所有结果）的地方：同一个问题常被多个方向各报一遍，不先去重就会派好几组 verifier 核验同一件事。

**但这一步极其容易只存在于注释里。** 真实案例：脚本里写着「需要 barrier：先汇总全部风险再去重，避免同一个风险被多个 verifier 重复核验」，而紧跟的代码只有 `flatMap` + 按严重度 `filter`，**没有任何去重逻辑**。

代价是可核实的：同一件事（某段带旧数字的死代码）被两个调研方向各报一次，两组 verifier 各自独立核验，**给出了两条相互矛盾的裁决** —— 综合阶段既拿到"成立"也拿到"不成立"。

**规则：去重要写成代码，不是写成注释。** 按什么去重（文件路径 + 关键词？标题相似度？）想不清楚，就把合并这一步显式交给一个 agent 做，也好过假装做过了。

同时做**分级**：只让高/中严重度的发现进入对抗核验，低severity 的直接带入结论但不单独核验。核验很贵，把预算花在会改变结论的发现上。

## 第二段：对抗核验

### 默认立场是"这是误报"

给 verifier 的立场设定要写死。实测有效的原文：

> 有人在调研时提出了下面这条风险。你的任务是【尽力推翻它】。默认立场是"这是误报"，只有当你亲自打开文件、跑命令看到确凿证据时才承认它成立。

关键是**"亲自打开文件、跑命令"** —— 不允许靠推理判断真伪。

### 把已知的误报模式直接告诉它

这是让核验真正有效的那一步。不写这段，verifier 会随机地怀疑；写了，它会去查真正容易错的地方。

下面四条是**某个代码仓库**的误报形态。**要照抄的是这个动作，不是这张单子** —— 换个对象，容易误报的东西完全不同：

> 特别注意这几类误报：
> - 把归档的旧版本文件里的旧数字，当成"当前产物里的过时数字"
> - 把代码注释、变量名、历史文档里的旧数字当成风险
> - 把"文件不存在"说成风险，但其实文件在另一个路径下
> - 数字对不上，但其实是四舍五入或不同口径

每次做这类编排，都花两分钟想一想"**这个领域里，看起来像问题但其实不是的，有哪几类**"，然后写进去。

### 用不同视角，而不是 N 个一样的怀疑者

派两个视角完全不同的 verifier，比派三个同样的 refuter 更能抓住不同的失败模式：

- **视角 A · 事实核对**：这件事**是不是真的**？去读文件、跑命令。
- **视角 B · 后果与行动**：**假设它是真的，它重要吗**？会不会改变某个决定、会不会让对外说错话？还是只是内部整洁度问题？用项目当前阶段的标准衡量：算 blocker、算待办、还是算噪音？

视角 B 抓的是另一类垃圾 —— **属实但无关紧要**的发现。它们最消耗读者注意力，因为无法反驳。

其他可用视角（按对象选）：多重比较/统计口径、样本量、能否复现、安全影响、成本。

### 核验对象里必须显式包含"规则"，不只是"主张"

对抗核验天然只审**已经被提出的主张** —— 它的输入是上游报上来的 findings 数组。但最贵的错误往往不是主张，而是**没人把它当成主张的规则**：

- **纳入/排除规则**（哪些行算数）
- **分组键 / 独立单元数**（几行算一个独立观测）
- **配对定义**（谁和谁可比）

这些东西从不进 findings 数组，因此**从头到尾没有任何 agent 被要求去证伪它们**。这与完整性批评者要解决的盲区是同构的：不在队列里的东西不会被核验。

规则：**把这几项当成 finding 显式塞进核验队列**，并要求核验方式是"从原始数据重新构造一遍再比对"，不是读预处理脚本、不是读产物。（这一段的方法见 `analysis-groundwork`。）

### 让核验者先复现数字，再攻击推论

要求核验者**先逐位复现被审结论的数字，确认算术无误，再单独攻击那一步推论** —— 并且「算错了」和「推错了」分开报。

不分开的话，一个算术正确但推论过头的结论容易被整条判成立（因为数字对得上），而一个算术有小误差但洞察正确的结论容易被整条推翻。

### verdict 不要只是布尔

让 verifier 除了"成不成立"，还输出一个**修正后的精确表述**：

```
{ refuted: bool,
  reasoning: '你实际做了什么、看到了什么',
  correctedStatement: '如果部分成立，给出精确的、你亲自核实过的表述（含文件:行号）' }
```

现实中大量发现是**"方向对但细节错"**。二值投票会把它们连同错误一起扔掉；`correctedStatement` 把它们救回来，而且救回来的版本比原来更准。

### 合并规则要匹配"漏报和误报哪个更糟"

两个 verifier 的结果怎么合并，是一个**要显式决定**的事：

- **宁可多报（怕漏）**：任一视角认为成立就保留，两个都认为成立标记为"双视角确认"。适合状态调研、安全排查 —— 漏掉一个真问题的代价高于多看一条。
- **宁可少报（怕吵）**：需要多数或全体认为成立才保留。适合要直接对外的结论、自动化流程的输入。

**默认不要用简单多数**，先问自己哪个方向的错误更贵。

## 第三段：综合

- **只用扛住核验的发现**合成结论；被推翻的不进正文。
- **把被推翻的清单也交给综合者**，明确标注「不要写进报告，仅供你判断哪些是误报」。这能防止它从原始调研材料里把同一条重新捞出来。
- 综合的输出也要 schema 化，而且**要照着读者的问题设计字段**，不是照着材料的结构设计。如果读者的问题是"我现在该干什么"，那就必须有一个"下一步动作"字段，且要求具体到"敲哪个命令、改哪个文件、找谁要什么"，禁止"进一步分析"这类空话。

---

## 第四段：完整性批评者（最容易省略，价值最高）

最后派一个 agent，**只做一件事：找这份结论缺了什么，不许夸它。**

### 它要回答的问题

> - 有没有哪个文件/模块/数据从头到尾**没被任何人打开过**？
> - 有没有已知的待办清单/承诺/悬而未决的问题，**没有在结论里被回应**？
> - 有没有把**不确定写成了确定**（或者反过来，把能算的说成"拿不到"）？
> - 有没有哪条建议**会把事情改坏**？
> - 结论有没有回答读者真正的那个问题？

### 它能抓到而前面几段抓不到的东西

前三段的每个 agent 都只看见自己那一块，**没有人站在读者的位置上看整体**。批评者的独特价值在这里，最重要的一类叫**取景漂移**：

> 真实案例，批评者的两句判词（一句在总评里，一句在它列的第一条缺失里）：
> 「问题出在报告的**取景**，不是它的算术。……它是一份**文档整改报告**，不是**项目状态报告**。」
> 「整份下一步动作十条里九条是改文件、一条是查邮件 —— 读起来像『文档整改清单』，不像『项目下一步』。」
>
> 根因：调研 agent 读的是文件，于是所有发现都是文件层面的；综合者忠实地综合了它们。**整个流水线诚实地回答了自己给自己提的问题，而不是读者的问题。**

同一次批评还抓出：三处把不确定写成确定（其中一处声称某个区间"拿不到"，实际三行代码就能算出来；另一处声称某系统里"零记录"，实际内容都在）、一条**会把事情改坏**的建议（它会推翻一个已经对外承诺过的口径）、以及**一整个没人负责的维度**（那次是"外部约束对『我们能对外说什么』的限制" —— 它不属于任何一条调研方向）。

后两类是纯增量：没有任何一个调研方向被指派去看它们，所以前三段结构上不可能发现。

### 让批评者也去抽查

批评者不能只做逻辑审查。要求它**独立复算几条关键断言** —— 上例里它自己从数据文件重算了核心效应量，确认与结论一致，然后才说"取证层面是扎实的，问题在取景"。**这让它的批评有了分量，也避免它变成为批评而批评。**

### 三个容易做错的细节

- **把上游全部原始素材也附给它，不只是结论草稿。** 只拿到草稿的批评者只能产出文风建议；能回到素材的批评者才能回答"素材里明明有的东西，为什么没进结论"。真实案例：一份批评者 prompt 正文写着"以及它背后的调研素材"，脚本里却只插值了草稿本身 —— 素材根本没附上。
- **不要在提问里预设某个否定结论。** 写"去验证 X 是不是真的不存在"，不要写"如果 X 什么都没找到，草稿有没有诚实说明这一点" —— 后者把批评者锚定成只审措辞。上例里最有价值的那条发现，恰恰来自批评者**无视了这句锚定、自己跑了一遍搜索**。那是运气。
- **用三段式 schema 约束输出：缺什么 / 为什么重要 / 具体怎么补。** 写不出"怎么补"的批评多半是废话。同时要求它区分"明确的错误"和"判断分歧" —— 后者写进待决项交人拍板，不许把自己的偏好包装成缺陷。

### 批评者的产出怎么用

它给的是**待处理清单**，不是最终判决。逐条判断：真的缺 → 补；理解偏差 → 说明；意见不同 → 记下分歧。不要照单全收，也不要因为"报告已经写完了"就搁置。

## 规模怎么定

规模由**正交的调研方向数**决定，不是由"想要多认真"决定。

| 情形 | 量级 | 说明 |
|---|---|---|
| 摸清一个完整项目的现状 | 数十 agent | 6 路调研 × 每条发现 2 个 verifier，很快就上去了 |
| 按已定方案批量修改一个交付物 | 十几 agent | 每条改动一个取证 + 一个实施，加一轮复核 |
| 回答一个有明确边界的问题 | 5–7 agent | 几个并行子问题 + 一个综合 |
| 一个方向就能答的 | 0 | 自己做 |

**agent 数量主要由「有几个独立的取证地盘」和「有几条发现值得核验」推出来**，不要先定一个数再去凑。

## 不相信任何未经自己复核的转述

这条贯穿全程，包括对这套编排本身。

- **workflow 报的结论，会改变决定的那些，自己回原始数据复核。** 真实案例：一次编排报出的结论会推翻主对话前几轮反复说过的话 —— 于是没有直接采信，而是自己跑命令、拿盘上的生产数据独立比对，才确认。
- **"已经验证过了"不算证据。** 真实案例：复核声称某检查全部通过，自己实跑发现 2 个问题，而且正好在核心页面。
- **"写了代码"和"确认代码能用"是两个 claim。** 承诺验证前不要说 done。
- **认错要清楚**：说错了就明说哪里说错了、根因是什么、影响了哪些已经说出去的结论。不要粉饰，也不要甩锅给 agent —— 派活的是你。

## 已知的失败模式

- **取景漂移**（见上）：调研的框架被对象的结构绑架，答的不是读者的问题。**对策**：动手前先写下"读者会拿这份结论做什么决定"，综合的 schema 照着这个设计。
- **规模不等于质量**：大编排的产出里有相当一部分是低价值的。核验和批评这两段才是把规模变成可信度的地方 —— 只加调研方向不加核验，是在批量生产待核实的猜测。
- **空票要能被容忍，而不是让整条发现消失**：合票逻辑写成"先过滤掉空返回、再判断剩下的里有没有认为成立的"。某个 verifier 没回来时，这条发现应该走"存活但只有单视角"，而不是因为 null 参与布尔运算被静默判死。
- **同一文件的并行修改会互相覆盖**：并行的边界是文件，改同一个文件的任务必须串行。
- **跑到一半发现了会改变前提的事实 —— 停掉、写进简报、重跑，不要让它跑完。** 真实案例：一次编排刚进备料阶段，主对话自己算出一个事实，推翻了简报里的一条前提。处理是立刻 TaskStop 停掉整个编排、把新事实补进共享 context、然后从头重投。**几十个 agent 带着一条错前提跑完，产出的是一份工整的错误** —— 比中途止损贵得多。

## 红旗表

| 想法 | 现实 |
|---|---|
| 「派了 6 个 agent 覆盖得挺全，可以写结论了」 | 没人试图推翻过这些发现。误报比例不低。 |
| 「workflow 说验证过了」 | 自己再跑一遍。别人的"验证过"不算数。 |
| 「批评者那段就省了吧，结论已经挺完整」 | 那段抓的正是"你不知道自己不知道"的东西。 |
| 「多派几个一样的怀疑者更保险」 | 视角相同 = 失败模式相同。换视角，不是加人数。 |
| 「投票多数决就行」 | 先问漏报和误报哪个更贵，再定合并规则。 |
| 「这条发现方向对、细节错，扔了吧」 | 让 verifier 给出修正后的精确表述，救回来。 |
| 「结论覆盖了对象的每个部分，很完整」 | 覆盖对象 ≠ 回答读者的问题。 |
| 「任务复杂，多派点 agent 总没错」 | 装得下就自己读。编排的开销是实的。 |
| 「去重那步我在注释里写清楚了」 | 注释不会去重。同一件事会拿到两条相反裁决。写成代码。 |
| 「已经跑到一半了，让它跑完再说」 | 前提被推翻了就停。带着错前提跑完，产出的是一份工整的错误。 |
| 「这六个调研方向挺全的，下次照抄」 | 切法是从任务性质推出来的。换个任务照抄就废了。 |
